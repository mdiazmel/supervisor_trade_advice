# Analyse du 2026-09-29

## Verdict

**Aucun digest n'a ete publie aujourd'hui.** La chaine de publication s'est tue
pour la premiere fois depuis sa mise en service : 12 seances consecutives
publiees, aucune manquante, puis rien. Je n'ai donc aucune donnee de marche a
analyser — ce rapport porte uniquement sur la panne.

Ce n'est pas un retard : le digest est attendu dans une fenetre deterministe de
90 secondes et il a **64 minutes de retard** au moment ou j'ecris. L'agent
detenait **trois positions a la derniere mesure connue**, et personne ne les
observe depuis la cloture d'hier. **Action humaine requise ce soir.**

## Constats

**1. L'absence est mecanique, pas une variation d'horaire (constat mecanique).**

`deploy/agent-trade-digest.timer` declenche `Mon..Fri 16:30 America/New_York`
avec `RandomizedDelaySec=120` : la publication tombe donc entre 16:30 et 16:32
New York. Les 12 publications automatiques du 09-11 au 09-28 respectent cette
fenetre sans exception :

| | Premiere (09-11) | Derniere (09-28) | Amplitude |
|---|---|---|---|
| Horodatage UTC | 20:31:15 | 20:30:24 | **90 secondes** |

Douze jours ouvres du 09-11 au 09-28, douze digests, **zero manquant**. Il est
17:36 New York : le digest a **64 a 66 minutes de retard** sur une fenetre dont
il n'est jamais sorti de plus de 90 secondes. Le depot est bien a jour — j'ai
verifie que mon clone local est identique a `origin/main` avant de conclure.

Deux hypotheses sont **ecartees** :

- **Jour ferie / seance sans trading.** Le timer est `Mon..Fri` sans calendrier
  boursier, et un journal vide produit quand meme un fichier, donc un commit.
  Un jour creux donnerait un digest vide, pas une absence.
- **VM tombee puis redemarree.** Le timer porte `Persistent=true` : systemd
  rejouerait le passage manque au redemarrage. Rien n'est arrive, donc soit la
  VM est toujours a terre, soit l'unite a tourne et **echoue**.

**2. Le garde-fou que je proposais hier n'est pas en cause (hypothese ecartee).**

Mon rapport du 09-28 avertissait qu'un merge de `supervision/2026-09-28`
transformerait une degradation silencieuse en **refus de demarrer** si le `.env`
de la VM portait encore `ATA_SENTIMENT_EFFORT`. C'etait le suspect naturel. Il
est innocent : la branche **n'est pas fusionnee** (son commit `6da4253` est
toujours absent de `main`), et `main` n'a pas bouge depuis `449b60f` du 09-28
a 16:49 — une revision **anterieure a la seance du 09-28, qui s'est bien
publiee**. Le code qui tourne aujourd'hui est exactement celui d'hier.
**Inutile de chercher de ce cote.**

**3. Un echec de publication detruit le digest du jour au passage suivant
(constat mecanique, verifie par lecture du code — c'est le point urgent).**

Si la panne est dans l'etape de `push` et non dans la generation, le digest du
09-29 **existe sur la VM**, commite mais non pousse, dans
`/opt/agent-trade-alpaca/.reports-repo`. Or `push-digest.sh` ligne 58 fait, a
chaque passage :

```bash
git -C "$CLONE_DIR" reset --hard "FETCH_HEAD"
```

Ce `reset --hard` **ecrase le commit local non pousse**. La regeneration qui
suit tourne avec `DAYS=1`, et `build_digest` ne couvre alors que le jour courant
(`digest.py:151`) : le 09-29 n'est pas reconstruit. **Demain 16:30 New York, le
digest du 09-29 disparait** — silencieusement, comme le reste.

La bonne nouvelle : **la donnee source survit**. Le journal n'a aucune purge
(pas de retention, pas de pruning dans le code) et vit dans le volume `/data`.
Le 09-29 reste donc reconstructible apres coup :

```bash
docker compose -f deploy/docker-compose.yml run --rm --no-deps agent \
  digest --days 2 --output /reports
```

**4. La panne est silencieuse de bout en bout (constat mecanique).**

`agent-trade-digest.service` est un `Type=oneshot` **sans `OnFailure=`** et sans
aucune notification. Quand `push-digest.sh` sort en erreur (`set -euo pipefail`),
systemd marque l'unite en echec et **personne n'est prevenu**. Le seul detecteur
de cette panne, c'est ce rapport — avec une latence d'une heure, et seulement
les jours ouvres. Si la meme chose se produit un vendredi, la cecite dure
**jusqu'au lundi**.

**5. Trois positions sont ouvertes et non observees (constat mecanique).**

Derniere mesure connue, cloture du 09-28 :

| Position | Qte | Latent |
|---|---|---|
| AAPL | 18,0 | -8,72 $ |
| AMD | 5,9285 | +15,42 $ |

Equity **100 312,11 $**, exposition brute **0,2045** (~20 500 $ exposes),
`kill_switch_events` **0**. Rien d'alarmant *a la derniere mesure* — mais elle
date de plus de 24 heures. **Je ne sais pas si l'agent a traite aujourd'hui.**
Les deux scenarios sont opposes et je ne peux pas les departager d'ici :

- **L'agent tourne, seule la publication est cassee** : le risque est maitrise,
  l'incident est cosmetique et se rattrape (constat 3).
- **L'agent est arrete** : les trois lignes sont ouvertes **sans kill switch ni
  rebalancement**. C'est le scenario qui justifie de regarder ce soir.

C'est la question a trancher en premier, et elle se tranche en une commande
(section « A surveiller »).

**Securite.** Aucun digest a analyser, donc aucune surface d'injection ce jour.
Je n'ai lu aucun `.env` ni aucun secret, et n'ai pousse sur aucune branche par
defaut.

**Deux correctifs de fiabilite sont identifies, et je ne les pousse pas
aujourd'hui.** Je les decris ici pour que la prochaine session les reprenne :

**a. Ne plus detruire un digest non pousse** (constat 3). Remplacer le
`reset --hard` inconditionnel par une reprise qui preserve un commit local en
attente, ou regenerer avec un `DAYS` couvrant les jours non publies.

**b. Rendre l'echec bruyant** (constat 4). Un `OnFailure=` sur
`agent-trade-digest.service`, pour qu'une publication ratee se signale au lieu
d'attendre que le superviseur s'en apercoive une heure plus tard.

**Pourquoi aucune branche ce soir.** Le skill impose une reproduction de
l'incident et un test qui verrouille le correctif. Or **je ne connais pas encore
la cause** : je n'ai pas acces a la VM, et corriger le chemin du `push` alors
que la panne est peut-etre dans la generation — ou que la VM est simplement
eteinte — reviendrait a deviner. Ces deux correctifs touchent des scripts de
deploiement, pas le chemin de decision : ils peuvent attendre un diagnostic.
**Priorite ce soir : retablir l'agent, pas durcir le script.**

## A surveiller

- **Trancher « agent vivant » contre « agent mort », d'abord.** C'est la seule
  question qui engage de l'argent (constat 5) :
  ```bash
  systemctl status agent-trade          # l'agent tourne-t-il encore ?
  docker compose -f deploy/docker-compose.yml ps
  ```
  Si l'agent est arrete, les trois positions du constat 5 sont sans surveillance.

- **Puis la cause de l'echec de publication**, avec l'outil deja prevu pour ca :
  ```bash
  ./deploy/check-digest.sh
  journalctl -u agent-trade-digest.service --since '2026-09-29 16:00' --no-pager
  ```
  `check-digest.sh` affiche le resultat du dernier passage et les dernieres
  lignes du journal, sans jamais afficher le token.

- **Sauver le digest du 09-29 avant demain 16:30 New York** (constat 3), si le
  commit local existe :
  ```bash
  git -C /opt/agent-trade-alpaca/.reports-repo log --oneline -3
  git -C /opt/agent-trade-alpaca/.reports-repo status
  ```
  S'il est la, le pousser a la main avant le prochain passage du timer. Sinon,
  le reconstruire depuis le journal avec `--days 2` (commande au constat 3).

- **Une piste concrete si la generation a reussi et le push a echoue :
  l'expiration du token.** `ATA_SUPERVISOR_GITHUB_TOKEN` est un PAT
  fine-grained, et ceux-ci expirent a date fixe. Le mode d'echec colle
  exactement a ce qu'on observe : l'agent traite normalement toute la journee,
  le digest se genere, et seul le `push` retourne 403. C'est une **hypothese**,
  pas un constat — le `journalctl` ci-dessus la confirme ou l'infirme en une
  ligne. Je n'ai evidemment pas lu le token.

- **Si le digest du 09-30 arrive normalement demain**, l'incident aura ete
  ponctuel : il restera a recuperer le 09-29 et a decider des deux correctifs de
  fiabilite. **S'il manque aussi**, la panne est installee et les correctifs
  deviennent secondaires devant le retablissement de la VM.
