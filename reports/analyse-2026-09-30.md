ponctuelle : elle est installee. Aucune donnee de marche depuis la cloture du
09-28, soit plus de 48 heures sans observation des trois positions ouvertes.

Mais le contexte a change et il change la conclusion : **l'humain a pousse trois
commits d'infrastructure aujourd'hui entre 16:32 et 17:01 New York**, qui
codifient la VM en Terraform et ajoutent un allumage/extinction programme. La
panne ressemble donc a une **migration d'infrastructure en cours**, pas a un
incident non detecte. L'urgence d'hier (« regarder ce soir ») tombe.

Elle est remplacee par une autre, plus concrete : **la procedure Terraform
documentee detruit le journal**, seule source permettant encore de reconstruire
les seances 09-29 et 09-30. C'est le point a traiter avant le prochain
`terraform apply`.

## Constats

**1. Deux seances manquantes, et ce n'est pas un clone perime (constat mecanique).**

13 digests publies du 09-10 au 09-28, aucun manquant, puis rien. J'ai verifie
avant de conclure que mon clone est identique a `origin/main` (`ba6f91b`) apres
`git fetch` : le depot de digests n'a recu **aucun commit** depuis
`Analyse 2026-09-29`. Le dernier digest reste `digest-2026-09-28.json`.

Il est 17:37 New York ; la fenetre de publication est 16:30–16:32 (timer
`Mon..Fri 16:30 America/New_York`, `RandomizedDelaySec=120`). Le 09-30 a donc
~66 minutes de retard, exactement comme le 09-29.

**2. Un agent mort ne peut pas expliquer un digest absent (constat mecanique,
verifie par lecture du code — ceci elimine une moitie du diagnostic).**

J'ai teste l'hypothese « le conteneur est tombe, donc plus de digest ». Elle est
**fausse**, pour deux raisons independantes :

- `push-digest.sh` genere le digest avec
  `docker compose run --rm --no-deps agent digest`. Le `--no-deps` et le
  conteneur jetable rendent la generation **independante de l'agent qui tourne**.
- `build_digest` nomme le fichier `digest-<date du jour UTC>`
  (`digest.py:581`, `period_end = wanted[-1]`) et retourne un `_empty_digest`
  quand le journal est vide (`digest.py:158`). Un journal vide produit donc
  quand meme un **fichier neuf et date**, donc un diff, donc un commit.

J'avais aussi envisage la variante « le digest se regenere a l'identique, donc
`git diff --cached --quiet` sort 0 et le timer enregistre un succes silencieux ».
Elle est **ecartee** par le meme mecanisme : le nom du fichier porte la date du
jour, il y a toujours un fichier nouveau.

**Consequence** : l'absence totale de fichier implique le **systeme hote, la VM
ou l'etape de push** — jamais le moteur de trading. Inutile de chercher du cote
de la strategie ou du conteneur.

**4. La procedure Terraform documentee detruit le journal (constat mecanique —
c'est le point urgent du jour).**

Le journal est la seule source permettant de reconstruire les seances 09-29 et
09-30 (plan de recuperation d'hier : `digest --days N`). Il vit dans
`/opt/agent-trade-alpaca/.state/journal` : `docker-compose.yml` monte
`../.state:/data` et fixe `ATA_STATE_DIR=/data`. Ce repertoire est sur le
**volume racine** de la VM — la configuration Terraform ne declare aucun volume
de donnees separe, seulement `root_volume { volume_type = "sbs_volume" }`.

Or `infra/README.md` documente deux operations de routine qui l'effacent :

- `terraform destroy` ;
- `terraform apply -replace=scaleway_instance_server.agent`, explicitement
  recommande « apres une modification de `cloud-init.yaml` » — **et `edd9db4` a
  modifie `deploy/cloud-init.yaml` aujourd'hui**.

L'etape suivante que la documentation prescrit apres le commit d'aujourd'hui est
donc precisement celle qui detruit le journal, et avec lui l'historique des deux
seances manquantes ainsi que l'etat de suivi des bases de cout.

**A faire avant tout `terraform apply` ou `destroy`**, si l'ancienne VM existe
encore :

```bash
ssh trader@<ancienne-IP> 'tar czf - -C /opt/agent-trade-alpaca .state' > state-backup-2026-09-30.tgz
```

**5. Le `reset --hard` d'hier est confirme, et son effet s'accumule (constat
mecanique).**

`push-digest.sh` fait a chaque passage `git -C "$CLONE_DIR" reset --hard
"FETCH_HEAD"` avant de regenerer avec `DAYS=1`. Tout commit local non pousse est
donc detruit au passage suivant, et la regeneration ne couvre que le jour
courant. Si la generation a reussi et que seul le `push` echoue, les digests
09-29 **et** 09-30 sont deja perdus dans le clone `.reports-repo` ; seul le
journal (constat 4) permet de les retrouver.

**6. Revue de `infra/scheduled-power` : pas de conflit avec le digest, mais un
couplage non protege.**

C'est la crainte naturelle, je l'ai verifiee : **il n'y a pas de conflit.**
`start_schedule = "0 9 * * 1-5"`, `stop_schedule = "30 18 * * 1-5"`, fuseau
`America/New_York`. La VM est donc allumee de 09:00 a 18:30, ce qui couvre le
digest (16:30–16:32) et le superviseur local (17:30). Le choix du fuseau
boursier pour les deux mecanismes est correct.

Le point de vigilance est ailleurs : **rien n'empeche de reculer `stop_schedule`
avant 16:32**. Le jour ou quelqu'un l'avance pour economiser, la publication
s'arrete definitivement et silencieusement, et le lien entre les deux fichiers
(`infra/terraform/variables.tf` et `deploy/agent-trade-digest.timer`) n'est
ecrit nulle part. Une ligne de commentaire dans `variables.tf` suffirait ; a
mentionner en revue de la PR.

**Aucune branche de code aujourd'hui non plus, et c'est delibere.** Les deux
correctifs de fiabilite identifies hier restent valables et non pousses :

- **a.** Ne plus detruire un digest non pousse (constat 5) : remplacer le
  `reset --hard` inconditionnel par une reprise preservant un commit local en
  attente, ou regenerer avec un `DAYS` couvrant les jours non publies.
- **b.** Rendre l'echec bruyant : un `OnFailure=` sur
  `agent-trade-digest.service`, aujourd'hui `Type=oneshot` sans aucune
  notification.

Trois raisons de ne pas les pousser maintenant, par ordre de poids :

1. **La cause reste inconnue.** Le skill exige une reproduction de l'incident et
   un test qui verrouille le correctif. Je n'ai pas acces a la VM et le constat 2
   ne fait qu'eliminer une moitie du diagnostic ; corriger le chemin du `push`
   alors que la VM est peut-etre simplement detruite serait deviner.
2. **L'infrastructure bouge sous nos pieds** (constat 3). Pousser une branche sur
   les scripts de deploiement pendant une migration en cours ajoute du conflit,
   pas de la fiabilite.
3. **Aucun harnais n'existe pour ces scripts** : rien dans `tests/` ne couvre
   `push-digest.sh`. Le correctif (a) demanderait d'en construire un, ce qui
   n'est pas le plus petit changement possible tant que la cause n'est pas
   etablie.

Ces deux correctifs se traitent proprement une fois la nouvelle VM stable, et
ils touchent le deploiement, pas le chemin de decision : ils peuvent attendre.
